# Enabling NIP-29 groups safely on the shared relay

**Status (2026-10-29):** scoping change built (`internal/groups/scope.go`), proven
on staging only. `GROUPS_ENABLED` stays unset in production. The production
groups key and the Space migration are separate decisions (see "Not in this
change").

## The problem

relay.cloistr.xyz is a shared relay: profiles, notes, Stash, NIP-46 sign-in and
fleet gift-wrap threads all live on it. relay29 (v0.5.1) is written for a
relay that does nothing but groups. Wired the way `cmd/relay/main.go` used to
wire it, turning `GROUPS_ENABLED` on would:

1. Refuse every event without an h tag: `missing group (`h`) tag`
   (relay29 `event_policy.go:18`). That covers profiles, notes, follows, Stash
   and sign-in.
2. Refuse every REQ without h/e/a/ids: `invalid query, must have 'h', 'e' or 'a' tag`
   (`filter_policy.go:82`).
3. Refuse fleet gift-wrap thread buckets (kind 1059 with an h tag that is
   not a group): `group 'bucket-…' doesn't exist`.
4. Panic in the `AddToPreviousChecking` save hook on any event outside a group
   (nil group dereference).
5. Return results twice: relay29's query handlers were appended next to the
   store's, and khatru does not deduplicate.
6. Leak private groups even with 1 and 2 fixed. relay29 checks privacy only on
   group-shaped REQs, so `{"kinds":[9]}`, an `ids` lookup, a COUNT, or a live
   subscription would return private group messages to anyone.

## (a) The code change

`groups.Wire` attaches relay29 with every handler scoped to NIP-29 traffic.

- **NIP-29 traffic** means a NIP-29 kind (9000-9022 moderation/join/leave,
  39000-39003 metadata), or an event whose h tag names a group relay29 knows.
  An h tag alone does not count, because gift-wrap thread buckets use h tags.
- **Writes:** relay29's RejectEvent rules and save hooks run only on NIP-29
  events. `AddToPreviousChecking` runs only when the group exists.
- **REQ policy:** relay29's filter rule runs only on group REQs (metadata kinds,
  or #h naming a known group).
- **Queries:** group REQs are served only by relay29. Every other REQ is served
  only by the store, so nothing comes back twice. Store results are filtered
  so an event tagged with a private group is dropped unless the reader is a
  member.
- **COUNT:** for an ordinary COUNT, the events in private groups the reader can't
  see are subtracted (a second count of the same filter with `#h` set to those
  groups). A group COUNT on a private group the reader isn't in returns 0.
- **Live subscriptions:** a `PreventBroadcast` hook withholds private-group
  events from subscribers who aren't members.

`Wire` wraps the QueryEvents/CountEvents handlers already on the relay, so it
must be called after all of them are registered (it is, in `main.go`).

### Tests (`internal/groups/scope_test.go`)

These run against the real relay29 library on a real khatru relay with an
in-memory store. Four failed against the old wiring (fail-first); the two
marked "guard" pass on both and exist to show the scoping does not weaken
relay29's own group rules.

| Test | Proves |
|------|--------|
| `TestWire_OrdinaryEventsAccepted` | kinds 0, 1, 3, 30078, 24133, ungrouped 9, and a 1059 thread bucket are accepted with groups on |
| `TestWire_OrdinaryREQsUntouched` | authors+kinds, #p, #e, ids, Stash #d, bucket #h and kind 9 are not refused, return exactly what the store returns, each event once, and COUNT matches |
| `TestWire_GroupRulesStillApply` (guard) | a group kind without h, moderation in an unknown group, a non-member moderating, and client-signed 39000 are refused; a member can post |
| `TestWire_GroupMetadataServedOnceFromRelay` (guard) | metadata comes back once, generated by relay29 |
| `TestWire_PrivateGroupDoesNotLeak` | anonymous users and non-members are refused on #h, and get nothing from plain kinds/ids/authors REQs or COUNT; the member gets everything |
| `TestWire_PrivateGroupNotBroadcastToOutsiders` | live private messages go only to members; public group messages and ordinary notes reach everyone |

### Known limitations (resolve before production)

- **Unlocked membership reads.** relay29 guards each group's member map with an
  unexported lock. `Wire` reads membership and the private flag without it, the
  same way relay29's own query handlers do. A membership change racing a read
  is a Go map race, and that can crash the process. Fix: a small upstream
  patch or a fork exposing a locked accessor.
- **Private group metadata by id.** relay29's `MetadataQueryHandler` returns a
  private group's name and about to anyone who asks for its d tag. Members are
  not exposed (`MembersQueryHandler` checks). This is upstream behaviour.
- **Id collisions.** A gift-wrap bucket tag that happens to equal a group id
  would be treated as that group. Group ids are random, so this is unlikely,
  but it is not impossible.

## (b) Space's existing projects: not in this change

With groups on, relay29 owns kinds 39000-39003. Space's client-signed
39000/39002 are refused on write and are no longer served for metadata REQs.
Space projects therefore need migrating to relay-signed groups (a relay-signed
9007 create, 9000 put-user per member, and 9002 for name/private) **before**
groups go on anywhere Space users are. Space also has to switch to moderation
events for membership. This goes to the orchestrator and cloistr-space and is
not part of this change.

## (c) Staging proof

1. Staging overlay only (`cloistr-config overlays/staging/relay`): set
   `GROUPS_ENABLED=true`, `GROUPS_ALLOW_PRIVATE=true`, and a groups key that
   exists only on staging, held in a staging Secret.
2. Run the same probe against staging with groups on and against staging with
   groups off. Ordinary publish and read for kinds 0, 1, 3, 30078 and NIP-46
   must give identical results.
3. Group cases: create a public and a private group; a member posts; a
   non-member is refused on #h and sees nothing on plain/ids/COUNT REQs; the
   member sees everything.
4. Only after this is green: production key custody and the Space migration go
   to the orchestrator. No production change ships with this.
